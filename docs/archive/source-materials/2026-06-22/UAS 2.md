# LoveEngine 2026 Skill 设计说明书（UAS / UHAH 1.0 整合版）

## 1. 文档目的

本文档用于替换原 `UAS.md` 的“仅合约草图”版本，统一吸收以下两部分内容：

1. `UAS.md` 中已有的四合约架构与核心业务流程。
2. `LoveEngine Skill设计-Hermes.md` 中已有的 Skill 模块、角色、页面、开发规划与 UAS / UHAH 设想。

本版以 **Skill 设计** 为主线，以 **UAS 1.0 / UHAH 1.0 的最小可执行方案** 为落地范围，对原文中的职责重叠、模块边界不清、合约数量冲突、UHAH 空白、时间单位不一致等问题做统一收敛。

## 2. 产品定位

**产品名称**：LoveEngine 2026  
**产品形态**：一个面向普通用户、见证者、支付公司代理人的 AI + Web 3 协调 Skill  
**产品目标**：

- 完成 PoL / UAS / UHAH 的解释、教学与共识建立；
- 提供 UTO 总账、个人账、本企业补偿账的计算、展示与审计入口；
- 为见证者治理提供工作站、提案、投票、证据留存与公众意见汇总能力；
- 为支付公司提供直播排期、用户数提报、协议签署、成本补偿申请与公开透明面板；
- 以最小链上结构实现“公开总账可监管”，而不是试图一步到位做全球支付基础设施。

**一句话定义**：  
LoveEngine 不是钱包，不是交易所，也不是通用支付网络。它首先是一个 **围绕 UAS / UHAH 运行的治理与透明化 Skill**，其次才是链上记账系统。

---

## 3. 范围与非范围

### 3.1 本期范围

本期只做 UAS 1.0 / UHAH 1.0 的过渡方案，强调“先跑通最小闭环”：

- 单一支付公司先行接入；
- UTO 仅作账本计量与监管透明，不做自由提现，不做二级市场流通；
- 关键操作通过直播 + 见证者治理 + 链上存证完成；
- Skill 负责解释、协调、见证、计算、审计与协议管理；
- 合约负责总账逻辑、提案治理、透明查询和企业存证；
- UHAH 与 UAS 分账，不混同，不直接做全球统一医保清算。

### 3.2 明确不做

- 不在 1.0 中尝试全球多支付公司并发接入；
- 不在 1.0 中发行可自由流通的货币型代币；
- 不在 1.0 中把所有监管都自动化到链上；
- 不在 1.0 中把全部医疗理赔规则统一为一个全球标准；
- 不在 1.0 中要求每个普通用户都持有 ETH 或直接操作智能合约。

## 4. 核心概念

### 4.1 PoL

PoL（Proof of Love）是该系统的价值共识与治理基础。对 Skill 而言，PoL 不是抽象口号，而是以下产品约束：

- 公共福利优先于投机属性；
- 透明、可核验优先于黑箱效率；
- 公共账本与企业账本必须可审计；
- 关键参数更新必须走见证治理；
- 任何与 UTO 相关的企业协作不得以商业利润最大化为目标。

### 4.2 UAS

UAS（Universal Abundant Supply）是面向全体用户的公共福利供给方案。在 1.0 中，其最小实现不是“直接发实物”，而是：

- 以 UTO 作为统一记账单位；
- 以支付 App 内部账本展示个人可用额度；
- 以链上总账提供公共监管入口；
- 以见证治理控制关键参数更新与企业补偿。

### 4.3 UHAH

UHAH（Universal Healthcare for All Humanity）是与 UAS 分离的医疗福利账本。它在 1.0 中的定位是：

- **单独记账**；
- **仅限医疗 / 健康保障类场景**；
- **对接各国现有医保体系，而不是替代它们**；
- **通过支付 App 与医疗服务方结算，不直接向个人提现**。

### 4.4 UTO

UTO 是 UAS / UHAH 账本中的统一计量单位。在 1.0 中它具有以下约束：

- 不是法币；
- 不是自由流通币；
- 不是投机资产；
- 不能直接提现；
- 它的核心作用是 **把总账、企业补偿账和规则参数公开化、可核验化**。

### 4.5 见证者

见证者是治理节点，不等于传统管理员。见证者通过 Skill 完成：

- 观看直播并核验关键操作；
- 对用户数更新、成本补偿、危机模式等提案投票；
- 收集公众意见并形成可追踪记录；
- 维护最低限度的公共透明与程序正义。

## 5. 设计原则

1. **Skill 优先**：先定义角色、流程、页面、权限和交互，再反推链上结构。  
2. **链上最小化**：只把必须公开、必须防篡改、必须共识的状态放上链。  
3. **账本透明优先于支付复杂度**：UAS 1.0 核心是透明可监管，不是支付炫技。  
4. **单合作方先行**：先解决防重复领用、防账本作弊、防企业套利，再扩张。  
5. **连续计算 + 每日展示**：链上用连续流公式，产品层保留“每天 6:00”这一感知锚点。  
6. **隐私最小暴露**：医疗、身份、发票等敏感数据默认不上链，只上链哈希与最小证明。  
7. **人工流程最小化，但不否认必要的人工判断**：特别是在首期企业合作、证据审核、灰度治理阶段。

## 6. 用户角色与权限

### 6.1 普通用户

能力：

- 学习 PoL / UAS / UHAH 基础知识；
- 查询个人 UTO 账本与解释；
- 查看公开总账、企业补偿账、治理提案结果；
- 观看公开直播与透明面板；
- 提交公众意见与问题反馈。

限制：

- 不直接修改链上参数；
- 不直接参与企业成本补偿审批；
- 不直接看到他人敏感医疗数据。

### 6.2 见证者

能力：

- 进入见证者工作站；
- 接收直播排期通知；
- 审核直播证据；
- 对治理提案投票；
- 发起补充说明、异议记录、证据哈希提交；
- 参与公众意见整理。

限制：

- 不能绕过提案阈值单独改参数；
- 不能私下变更企业账本；
- 连续两轮不参与投票会被系统清退。

### 6.3 支付公司代理人

能力：

- 注册企业协作信息；
- 签署非营利与协作协议；
- 登记直播计划；
- 在直播中提交用户数变更提案；
- 申请成本补偿；
- 查看本企业账本与审批状态。

限制：

- 不能直接修改链上总账；
- 所有关键操作需通过直播与见证投票；
- 不得将 UTO 相关服务利润化。

### 6.4 系统协调员（可选，非长期中心化角色）

说明：

- 原稿中存在“管理员筛选后备池”的描述，但又希望尽量去中心化。
- 因此本版把它重定义为 **首期临时协调角色**，仅负责首批候选人预审与资料去重。
- 一旦治理机制成熟，应改为“提名 + 见证者投票确认”或“公开申请 + 规则筛选”。

## 7. Skill 总体结构

LoveEngine Skill 由 5 个核心模块构成，外加 1 个横向 Agent 监管层。

### 模块 1：PoL 教育引擎

**目标**：完成价值共识解释、概念澄清、误解纠偏。  
**输入**：用户提问、常见误区、政策与参数版本。  
**输出**：对话式解释、FAQ、图表、简化说明。

**核心能力**：

- 解释 PoL、UAS、UHAH、UTO、见证治理；
- 解释为什么 UTO 不是现金，也不是投机币；
- 解释“链上总账”和“支付 App 内部账本”之间的关系；
- 为普通用户提供从零理解路径。

**典型页面**：

- 新手引导页；
- UTO 是什么页；
- 为什么需要见证者页；
- FAQ / Myth Busting 页。

### 模块 2：UTO 计算与补偿引擎

**目标**：把抽象账本变成可解释、可模拟、可审计的数字系统。  
**输入**：用户数、时间、参数版本、补偿申请、企业成本明细。  
**输出**：公共总账、个人账本推算、企业补偿推算、影响模拟。

**核心能力**：

- 计算全网 UTO 总账；
- 计算某企业合作范围内的累计应计额度；
- 计算企业成本补偿的建议值与审批值；
- 提供消费场景模拟器与经济影响说明器。

**关键补充**：

- 原始文稿中 `Rate = 用户数 × 52 UTO/天`，但公式又使用 `block.timestamp` 秒级时间差，单位不一致。
- 本版统一为：

```text
precision = 1e8
baseBalance: 以上次结算时点的累计 UTO（按 1e8 精度记账）
checkpointTime: 上次结算时间戳（秒）
ratePerSecond = activeUserCount * 52 * precision / 86400
currentBalance = baseBalance + (block.timestamp - checkpointTime) * ratePerSecond
```

- 产品层保留“每天 6:00 的发放感知”，但链上实现采用连续流计算，避免每天批量结算。

### 模块 3：见证治理引擎

**目标**：为见证者提供完整治理工作站。  
**输入**：候选人资料、提案、投票、证据哈希、公众反馈。  
**输出**：治理结果、签名状态、自动补位、治理日志。

**核心能力**：

- 候选见证者注册与资料提交；
- Waitlist / ActiveWitnesses 状态管理；
- 提案投票、阈值判断、投票超时处理；
- 连续两次不参与投票的见证者自动清退；
- 公众意见聚合与高优先反馈归档。

**初始参数建议**：

- 正式见证者：69 人；
- 后备池上限：207 人；
- 通过阈值：赞成票不少于 90%；
- 投票窗口：24 小时；
- 被动淘汰阈值：连续 2 次未参与投票。

### 模块 4：直播见证与透明度引擎

**目标**：把“关键动作必须公开”从口号变成工作流。  
**输入**：直播预约、直播链接、操作录屏、截屏、后台指标、时间戳。  
**输出**：直播排期、见证记录、异常提示、证据链索引。

**核心能力**：

- 直播计划登记；
- 直播前检查清单；
- 直播中关键步骤提示；
- 直播证据与提案绑定；
- 透明面板实时展示总账、企业账与提案状态。

**直播最小检查清单**：

1. 展示当前支付品牌与协作主体；
2. 展示当前用户总数来源页面；
3. 展示统计口径与时间点；
4. 现场提交链上提案；
5. 展示提案哈希 / 交易哈希；
6. 展示企业补偿申请明细时的成本类别与凭证哈希；
7. 全程录像并把证据摘要绑定到对应提案。

### 模块 5：协议管理与 UHAH 隔离引擎

**目标**：管理企业协作协议、补偿逻辑与 UHAH 独立账本。  
**输入**：企业协议、地区规则、医疗场景映射、补偿申请、危机模式提案。  
**输出**：协议状态、UHAH 账本、补偿审批状态、违约预警。

**核心能力**：

- 企业非营利承诺的存证；
- 企业成本补偿申请与审批；
- UHAH 独立账户体系；
- 国家 / 地区医保接口映射；
- 医疗服务白名单与危机模式切换。

### 横向层：Agent 监管与分析层

**目标**：降低人为审查负担，但不取代最终共识。  
**能力**：

- 对公众反馈自动聚类；
- 检测明显异常的用户数波动；
- 对企业补偿申请进行结构化审查；
- 自动生成见证摘要；
- 对直播内容进行基本 checklist 对照。

**边界**：

- Agent 只能给出提示与分析，不直接改链上状态；
- 最终批准仍需见证者投票。

## 8. UAS 1.0 业务规则

### 8.1 基本规则

- 单位：UTO；
- 初始基准：52.0 UTO / 人 / 天；
- 精度：小数点后 8 位；
- 统一起算日：2024-11-21；
- 展示锚点：每天早上 6:00；
- 账本性质：公共福利记账，不可提现，不可自由转账投机。

### 8.2 个人账户规则

个人用户在支付 App 中看到的不是链上余额本体，而是：

- 基于全局规则计算出的个人可记账额度；
- 在合作支付体系中的独立 UTO 账单视图；
- 与法币账单分离的福利账单。

### 8.3 企业账户规则

企业账户需维护两本独立账：

1. **UAS 供给账**：反映企业在本合作下为用户侧承担的福利记账规模；
2. **企业补偿账**：反映企业因提供公共服务而经治理批准的成本补偿额度。

两者不能混为“企业利润”。

### 8.4 用户数更新规则

建议分阶段：

- 首年：每周一次；
- 第二年起：每两周一次；
- 若发生大规模异常波动，可加开临时直播与临时提案。

### 8.5 成本补偿规则

补偿不等于企业随意报销。本版定义 4 类可审成本：

1. 系统接入成本：支付 App 改造、账单系统改造、接口开发；
2. 运营服务成本：客服、基础运维、风控处理；
3. 合规协作成本：审计、合规对接、必要法务支持；
4. UHAH 特殊成本：医保映射、医疗机构对账、危机模式扩容。

**审批条件**：

- 成本类别必须在允许范围内；
- 需给出金额、周期、用途说明；
- 需提交发票 / 合同 / 工单 / 系统日志等证明的哈希；
- 需在公开直播中说明；
- 需经见证者治理批准后计入企业补偿账。

**建议公式框架**：

```text
approvedCompensationUTO = fixedBase
                         + verifiedUserScaleCost
                         + verifiedOperationCost
                         + verifiedExceptionalCost
```

具体参数不写死在文档里，而由治理参数控制。

### 8.6 单支付公司先行规则

1.0 明确只接一家支付公司，原因不是技术自卑，而是为了先解决：

- 重复领用；
- 跨平台账本对不上；
- 企业互相甩锅；
- 监管责任不清；
- 医疗账本与普通消费账本串账。

## 9. UHAH 1.0 细节补充

原稿中 UHAH 只有一句“在支付 App 内与 UAS 隔离开，单独记账，对接各国现有的医保体系”，这远远不够。本版补成最小可执行方案如下。

### 9.1 定位

UHAH 1.0 不是全球统一医保制度，而是一个 **与 UAS 分离的健康保障账本层**，目标是：

- 承担基本健康保障相关场景的记账与补贴；
- 尽量复用各国现有医保 / 商保 / 医疗支付系统；
- 在不暴露隐私的前提下，实现公共透明与治理可审。

### 9.2 账户结构

每个合资格用户在支付 App 内有 2 个福利子账户：

- `UAS_ACCOUNT`
- `UHAH_ACCOUNT`

二者不可直接互转，避免：

- 把医疗保障额度挪作普通消费；
- 把 UAS 消费额度伪装成医疗报销；
- 企业在不同账本之间转移成本。

### 9.3 可使用场景

UHAH 1.0 只允许以下四类场景：

1. 基本门诊与住院自付部分；
2. 基本药品与慢病长期用药；
3. 预防性医疗，如体检、疫苗、孕产基础项目；
4. 经危机模式批准的特殊保障支出。

### 9.4 结算方式

默认不向用户直接提现吗。结算优先级为：

1. 用户在合作医疗机构或药房消费；
2. 支付 App 识别医疗场景码 / 商户分类 / 对接医保接口；
3. 先走当地医保或现有保障系统；
4. 剩余合规自付部分由 `UHAH_ACCOUNT` 抵扣；
5. 最终账单中单列显示“医保支付 / UHAH 支付 / 用户自付”。

### 9.5 对接模式

为了避免一开始把项目做成全球医保大一统怪物，1.0 只要求支持三种接口层：

- 国家医保 / 地区医保适配器；
- 合作医院 / 药房白名单接口；
- 医疗场景编码映射表。

### 9.6 危机模式

当出现局部或区域性危机时，可由见证者治理临时启用 `UHAH Crisis Mode`：

- 提高部分医疗类别的支付上限；
- 扩展白名单机构；
- 放宽某些预授权条件；
- 启用紧急补偿预算。

**危机模式必须满足**：

- 有明确生效时间与结束时间；
- 有适用地区与适用类别；
- 有链上提案编号与公开说明；
- 过期自动失效，避免永久滥用。

### 9.7 隐私与存证

医疗数据是最容易把项目送进地狱的部分，所以本版只要求：

- 链上只记录最小必要信息：事件 ID、哈希、类别、金额、时间；
- 病历、处方、身份证等原始数据不上链；
- 由支付公司或合作医疗方托管原始数据，并接受法定审计；
- Skill 只展示解释、状态和摘要，不暴露原始隐私。

## 10. 技术架构

## 10.1 结构总览

系统分为三层：

1. **交互层**：Web 界面、聊天界面、透明面板、见证者工作站；
2. **服务层**：API、数据库、消息队列、Agent 分析、证据存储、企业接口适配；
3. **链上层**：治理、流计算、公共账本、企业存证四类核心合约。

### 10.2 为什么统一为 4 个核心合约

原始资料一处写“4 个核心智能合约”，另一处又写“四合一智能合约”，但列出来其实是 5 项。这种文档冲突很典型，像极了人类开会时一边说简化一边偷偷加层。  
本版统一为：

- 4 个 **核心合约**；
- 若未来需要 Gas Relay / AA Paymaster / Token Vault，则视为 **适配层**，不是核心合约。

### 10.3 核心合约

#### 10.3.1 WitnessDAO

**职责**：

- 管理见证者注册、后备池、正式池；
- 管理提案、投票、阈值判断；
- 触发自动清退与自动补位；
- 在提案通过后调用 StreamingEngine / CorporateSink 的更新方法。

**核心状态**：

```text
candidatePool
waitlist
activeWitnesses
proposalSnapshots
missedVoteCounter
proposalWindow = 24h
approvalThreshold = 90%
activeTarget = 69
waitlistCap = 207
```

**提案类型建议**：

- `UPDATE_USER_COUNT`
- `APPROVE_CORPORATE_COMPENSATION`
- `UPDATE_SYSTEM_PARAMS`
- `ACTIVATE_UHAH_CRISIS_MODE`
- `DISABLE_UHAH_CRISIS_MODE`
- `CONFIRM_WITNESS_BATCH`

#### 10.3.2 StreamingEngine

**职责**：

- 根据通过后的用户数更新流速；
- 维护总账连续增长；
- 提供只读计算接口。

**核心状态**：

```text
checkpointTime
baseBalance
ratePerSecond
precision = 1e8
```

**关键接口建议**：

- `settleAndUpdateRate(uint256 newActiveUserCount)`
- `getCurrentTotalUTO() view returns (uint256)`
- `getCurrentRatePerSecond() view returns (uint256)`

#### 10.3.3 PublicSink

**职责**：

- 作为公共固定查询入口；
- 只读代理 StreamingEngine；
- 输出对公众更稳定的接口语义。

**关键接口建议**：

- `getTotalUTO()`
- `getRatePerSecond()`
- `getLastCheckpoint()`
- `getCurrentActiveUsers()`

#### 10.3.4 CorporateSink

**职责**：

- 记录企业协作声明；
- 记录直播计划；
- 存证非营利协议；
- 记录企业补偿账；
- 向前端提供企业账本查询接口。

**关键接口建议**：

- `registerCorporateProfile()`
- `scheduleLiveSession()`
- `storeAgreementHash()`
- `recordApprovedCompensation()`
- `getCorporateCSR()`
- `getUpcomingLiveSession()`

### 10.4 服务层组件

#### API 服务

负责：

- 对外提供统一 REST / RPC 接口；
- 封装链上读取；
- 把 Skill 页面和支付公司接口连接起来。

#### 数据库

存储：

- 用户资料索引；
- 见证记录；
- 直播计划；
- 公众意见；
- 医疗场景映射表；
- 证据哈希与原始文件索引。

#### 消息队列

负责：

- 投票提醒；
- 直播开始提醒；
- 异常用户数波动告警；
- 补偿申请状态通知。

#### 证据存储

原则：

- 原始视频、截图、票据、日志可存对象存储或受控文件系统；
- 链上仅保存哈希、索引和摘要。

#### Relayer / AA 适配层（可选）

原文提出“接受 ETH 捐赠用于支付 gas”。这一想法可以保留，但更适合作为 **Relayer / Paymaster 适配层**，而不是核心业务合约：

- 普通用户无需持有 ETH；
- 见证者关键操作可被代付 gas；
- 代付规则受治理配置控制。

## 11. 关键业务流程

### 11.1 见证者生命周期

1. 候选人通过 Skill 提交资料与钱包地址；
2. 初期由协调机制做去重与基础审核；
3. 合格者进入 Waitlist；
4. 当 ActiveWitnesses 少于 69 时自动补位；
5. 见证者可主动退出；
6. 连续两轮未投票者在结算时被动清退；
7. 补位动作与状态变更自动上链并同步到工作站。

### 11.2 用户数更新流程

1. 企业代理人提前登记直播；
2. 到时公开直播展示用户数来源页面与统计口径；
3. 企业代理人通过 Skill 提交 `UPDATE_USER_COUNT` 提案；
4. WitnessDAO 冻结本轮投票快照；
5. 见证者在 24 小时内投票；
6. 达到 90% 阈值后，WitnessDAO 调用 StreamingEngine 结算旧余额并更新新流速；
7. 前端总账自动更新展示。

### 11.3 企业成本补偿流程

1. 企业代理人准备补偿申请；
2. 上传成本明细与证明材料；
3. Skill 生成结构化摘要与哈希；
4. 在公开直播中说明申请内容；
5. 见证者投票；
6. 通过后将批准值写入 CorporateSink；
7. 企业补偿账更新并可供公众查询。

### 11.4 UHAH 结算流程

1. 用户在合作医疗场景消费；
2. 支付 App 识别为医疗分类；
3. 先调用当地医保 / 商保接口；
4. 剩余部分若符合规则则从 `UHAH_ACCOUNT` 抵扣；
5. 账单摘要入库，摘要哈希可选上链；
6. 异常场景可进入人工复核或危机模式处理。
